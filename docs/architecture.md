# Architecture

*English · [Italiano](it/architettura.md)*

## Basic idea

The Amiga game is a 68000 executable of about 270 KB (after decompression),
written in C with Aztec C plus about 9 KB of assembly for the blitter. Instead
of rewriting it straight away, we run it as it is inside a "minimal Amiga"
written in Rust, which contains only what the game actually uses.

```
            ┌────────────────────────────────────────────┐
            │  original Mad TV code (68000)               │
            └──────────┬──────────────────────┬──────────┘
        jsr -LVO(a6)   │                      │  direct access
      (A-line trap)    ▼                      ▼  to $DFFxxx registers
            ┌────────────────────┐   ┌───────────────────────┐
            │ os/: AmigaOS HLE   │   │ custom.rs: copper,     │
            │ exec, dos, gfx,    │   │ blitter, interrupts,   │
            │ intuition, vfs     │   │ mouse, CIA             │
            └─────────┬──────────┘   └──────────┬────────────┘
                      │                          │
                      ▼                          ▼
            ┌────────────────────┐   ┌───────────────────────┐
            │ adf.rs: ADF disks  │   │ render.rs: line-by-    │
            │ + saves on the PC  │   │ line display           │
            └────────────────────┘   └──────────┬────────────┘
                                                 ▼
                                     ┌───────────────────────┐
                                     │ window.rs + input.rs   │
                                     │ window, mouse, keys    │
                                     └───────────────────────┘
```

## The CPU

We use the `m68k` crate in "single step" mode (`CpuCore::step`), which returns
a `StepResult`. Two cases matter to us:

- `Ok { cycles }`: instruction executed; the cycles advance emulated time
  (beam position, copper, frame);
- `AlineTrap { opcode }`: the program executed a `$Axxx` opcode. It does not
  exist on the 68000: we use it as a "call to the emulated operating system".

Careful (see NOTES.md): every time we change the PC from outside,
`invalidate_prefetch()` must be called, and the interrupt level must be set
again on every instruction.

## The emulated operating system

Amiga libraries are jump tables at negative offsets from the base: the program
calls `jsr -198(a6)` for `AllocMem`, where a6 = ExecBase. We build libraries
in which every 6-byte entry contains:

```
$A000 | (library_number << 9) | function_index   ; trap
rts
nop
```

When the CPU hits the trap, `Os::handle_trap` decodes library and function,
runs the Rust implementation (in `os/exec.rs`, `os/dos.rs`...), puts the
result in d0 and emulates the `rts`. If the function is not implemented yet,
emulation stops with a message stating exactly which function is needed and
where it was called from: this way we implement only what is needed.

Library numbers: 0 exec, 1 dos, 2 intuition, 3 graphics, 4 icon, 7 internal
traps (program end, interrupt dispatcher, unexpected exceptions).

### Start-up environment

`Machine::boot_os` and `Machine::load_executable` recreate what AmigaDOS sets
up for a command launched from the Shell:

- ExecBase at address 4, with `AttnFlags` = 0 (68000) and PAL frequency;
- a Process struct with its CLI (command name, seglist, console);
- the executable loaded as `LoadSeg` would: every segment preceded by its
  length and the BCPL pointer to the next, relocations applied;
- user stack with return address (→ program end) and size;
- a0/d0 = arguments (`"s\n"`, as in the original startup-sequence).

The executable's Imploder decompressor was not rewritten: it runs on the
emulated 68000, exactly as on a real Amiga, and uses `FreeMem` to release its
own segments at the end.

### Virtual file system

`os/vfs.rs` mounts the ADFs by volume name (`MTV1:`, `MTV2:`, plus `DF0:`,
`SYS:`). Writes (saves) go to `save/<VOLUME>/...` on the PC, which is checked
first on reads too: the original ADFs are never modified.

## The custom chips

`custom.rs` holds all registers `$DFF000-$DFF1FE`. Implemented:

- **timing**: 454 CPU cycles per line, 313 lines per frame (PAL);
  VPOSR/VHPOSR consistent with the cycles;
- **interrupts**: INTENA/INTREQ; the corresponding 68000 level is presented to
  the CPU on every instruction;
- **copper**: executed line by line (MOVE, WAIT; SKIP ignored), restarting
  from COP1LC every frame. It is essential because the game uses an interrupt
  generated by the copper to keep time;
- **blitter**: full area mode (4 channels, shifts, masks, descending mode,
  fill); completes instantly;
- **mouse/keyboard**: JOY0DAT, POTGOR, CIA-A PRA (mouse buttons), CIA-A SDR
  (keyboard);
- **sprites**: SPRxPT pointers; the actual DMA is in the display.

## The display

`render.rs` draws the picture **line by line during emulation**: on every scan
line `Custom::advance` first runs the copper and then `Display::line`, which:

- reads the bitplanes from the current BPLxPT addresses and advances them by
  (words fetched × 2 + modulo), like the hardware DMA: the game's interleaved
  bitmaps and pointer changes in mid-screen work without special cases;
- uses the palette in force on that line (the copper can change it);
- handles sprite DMA (POS/CTL headers, pairs of data words, attached
  15-colour sprites) and draws sprites over the playfield;
- swaps buffers at the start of every frame: `display.front` is always the
  last complete frame, ready for the window or for a PNG.

It handles lores/hires (hires lines are halved in width), display window
(DIWSTRT/DIWSTOP), fetch (DDFSTRT/DDFSTOP), modulos and Extra Half-Brite.
Missing: sprite priorities, fine scrolling, dual playfield and HAM.

## Input

`input.rs` translates mouse and keyboard into the registers the game reads:

- mouse: JOY0DAT counters (1 count = 1 lores pixel), left button on bit 6 of
  CIA-A PRA, right button on bit 10 of POTGOR;
- keyboard: CIA-A SDR, with the Amiga keyboard encoding (code rotated left and
  inverted, bit 7 = release).

In the window (`window.rs`) the game pointer is kept aligned with the PC one:
every frame we read the pointer position from the game's variables
(`Machine::game_pointer`) and send the difference as mouse movement. The game
accumulates movements in the interrupt and applies them in the main loop,
sometimes a few frames late: `input::pointer_step` also reads the accumulators
and the pointer limits of the current screen (`Machine::game_mouse`), so it
never resends a movement already made.

## CPU speed

`Machine::cpu_speed` (percentage of an A500) changes how many chipset cycles
correspond to one CPU cycle: at 300% the CPU executes three times as many
instructions per frame. The game keeps its own time with the frame interrupt,
so the game pace does not change: only computation waits get shorter
(decompression and drawing of screens). Some animations, however, are timed by
the CPU and would speed up too; for this reason the window uses the
**automatic turbo** (`Machine::auto_turbo`): CPU at 100%, rising to
`turbo_speed` after every dos Open/Read and back to normal as soon as the game
calls its own function that reads the frame counter (`Machine::pacing_pc`),
that is when it starts synchronising with time again.

### Action scripts

`input.rs` also defines a small language to automate the game without a
window: `FRAME:action` entries (`goto X Y`, `move DX DY`, `click`, `key NAME`,
`type TEXT`, `shot NAME`...). It is used for tests, to reproduce a problem and
to compare behaviour with WinUAE. Example in `scripts/nuova-partita.txt`.

## Exceptions

A-line traps are our channel to the emulated operating system. The other
synchronous exceptions (TRAP #n, F-line, ILLEGAL) are taken by the CPU as on
the hardware, jumping to the vector: some programs (the `rai` intro) install
their own vector and use `TRAP #0` to switch to supervisor mode. Vectors not
installed by the program point to stubs that stop emulation with a message
("unexpected exception").

## The window

`window.rs` uses `minifb`. A `Frontend` keeps the window open for the whole
session and runs in sequence what the disk's startup-sequence did: the `rai`
intro in an emulated machine of its own (skippable with a click or a key), the
credits screen (`u3.lbm`, decoded by `iff.rs`), then the game in a new machine
(the intro is disabled by default: `--intro`). The picture is magnified by
integer pixels inside a margin (20 pixels by default): black at the top and
sides, while at the bottom the margin shows the display lines beyond 200. 50
frames per second. The PC cursor is hidden because the game draws the pointer.
Automatic fast forward while the screen is black (loading) and with F11; F12
saves a screenshot.

## Audio

`paula.rs` emulates Paula's 4 channels. For each channel: registers AUDxLC,
AUDxLEN, AUDxPER, AUDxVOL, AUDxDAT; when DMA is switched on (DMACON) the
channel loads pointer and length, reads the first word and raises the
interrupt (the program can already prepare the next block); at the end of the
block it reloads from the registers and raises it again. Each 8-bit sample
lasts AUDxPER cycles of the audio clock (3.546895 MHz, half the CPU clock):
time is the chipset's, so the pitch does not depend on the emulated CPU
speed.

Mixing follows the hardware (channels 0 and 3 left, 1 and 2 right).
Resampling to the sound card rate integrates the output over each interval
(moving average), then the fixed A500 low-pass (about 4.4 kHz) is applied and,
if the program switches it on through bit 1 of CIA-A PRA, the "LED" filter
(about 3.3 kHz, 12 dB/octave).

`audio.rs` opens the default device with `cpal` and queues the samples in a
buffer shared with the card's callback. The window emulates a frame only when
fewer than 3 frames of audio (60 ms) are left in the queue: the sound card
sets the pace, so neither gaps nor latency build up. During fast forward the
audio is discarded. Without an audio device the window falls back to a fixed
pace of 50 frames per second.

## Recording and replay

Emulation is deterministic: given the same input frame by frame, the machine
state is identical. `--record` writes to a script the mouse movements actually
sent to the game, the keys, the system clock (`clock`, which fixes what
DateStamp returns) and the CPU mode (`cpu`). Replayed with
`--headless --script @FILE`, it rebuilds the session: it is the tool for
analysing behaviour that can only be reached by playing.

## Overlay layer

`overlay.rs` draws shapes (outlines, transparent fills, lines) in game
coordinates, but at window resolution, after magnification, with masks
(`Mask`/`Unmask`) to leave game objects such as the dragged panel uncovered.
`enhance.rs` computes the shapes to show every frame by reading the game state
from emulated memory; the window composes them over the picture. The layer
exists only in development mode (`--dev`): by default the window shows only
the game.

## Machine copies and trial clicks

`Machine` implements `Clone`: RAM, custom chips and emulated operating system
are copied (the ADF disks are shared through `Arc`), the CPU registers go
through serialisation (`serde` feature of the `m68k` core + `bincode`),
because the core does not implement `Clone`. A copy costs about 2 ms and
evolves identically to the original. The copy has a read-only file system
(`Vfs::read_only`): writes and deletions are discarded.

The highlights use it to ask the game "if I clicked now, what would happen?"
(`enhance::probe_drop`): on the copy the left button is pressed, up to 6
frames are run and we check whether the dragged object has been released.
This way each room's rules stay those of the original game, without rewriting
them. A longer variant (`enhance::probe_landing`, ~85 ms, in a background
thread) lets the copy run until the game redraws the dropped object, to find
where it lands.

For analysis, the bus has a watchpoint (`Bus::watch`, a RAM range: every CPU
access ends up in `Machine::watch_log` with the instruction's PC) and the
machine has probe points (`Machine::probe_pcs`: when the CPU is about to
execute one of those addresses it records frame and stack).

## Memory

A flat 2 MB RAM, all treated as Chip RAM (the chips are emulated in software,
so the A500's 512 KB limit is not needed):

| Addresses | Use |
|---|---|
| `$000000-$0003FF` | exception vectors |
| `$001000-$001FFF` | supervisor stack |
| `$002000-$1FEFFF` | memory managed by AllocMem (libraries, process, game) |
| `$BFD000-$BFEFFF` | CIA |
| `$DFF000-$DFF1FF` | custom chips |
